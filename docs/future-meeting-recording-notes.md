# 会议录音总结后续需求备忘

状态：future / not in V1
日期：2026-07-04
关联文档：

- `docs/meeting-recording-v1-spec.md`

## 背景

会议录音总结 V1 先做独立会议模式：麦克风录音、实时滚动原文、会后 LLM 总结待办、本地会议记录、Markdown 导出、原始音频按最近 N 场保留。

以下能力在需求讨论中被确认有后续价值，但不进入 V1 成功标准。本文只做备忘，避免后续继续讨论时遗忘方向。

## 后续方向

### 1. 会议专用 ASR 配置

- 为会议模式提供独立 ASR provider（语音转文字服务商）配置，不再完全复用全局短口述 ASR。
- 支持在线 ASR 和本地 ASR 在会议模式内同时作为可选项，并允许用户选择、切换。
- 会议模式需要独立保存 ASR 配置，不影响现有短口述链路。
- 需要处理会议中切换 provider 的边界：是否允许热切换、切换时是否产生新分段、旧 provider 失败如何标记。

### 2. VAD 与更自然的分段

- 接入 VAD（Voice Activity Detection，语音活动检测）优化会议原文分段。
- 目标是让段落按自然停顿生成，而不是完全依赖 ASR final segment（语音识别最终片段）。
- 需要评估 VAD 与不同 ASR provider 的职责边界：由 ASR 返回分段，还是 OpenLess 本地先切音频。
- 需要避免 VAD 误切导致语义断裂，尤其是中文短停顿和多人抢话场景。

### 3. 说话人分离

- 接入 speaker diarization（说话人分离），把 V1 默认的“未区分”升级为“发言人 1 / 发言人 2 / ...”。
- 支持实时区分发言人：会议进行中界面直接显示“发言人 A / B / C”等标签。
- 会议结束后继续保留说话人标签，会议原文、总结引用和导出内容都能带上说话人信息。
- 需要支持会后手动重命名说话人，例如把“发言人 1”改成真实姓名。
- 需要明确说话人标签的可信度：低置信度片段应允许显示为“未确认”或保留原标签。
- 需要评估在线服务、本地模型和混合方案的成本、延迟、隐私与准确率。

### 4. 实时标点与文本清理

- V1 实时区域展示 ASR 原始结果，结束后统一清理标点和分段。
- 后续可接入实时 punctuation restoration（标点恢复）和 text normalization（文本规范化）。
- 需要避免实时文本频繁回写造成闪动、滚动位置跳动和用户误以为内容已最终确认。
- 可考虑 UI 上区分 partial（临时片段）和 final（最终片段）。

### 5. 字幕级低延迟流式体验

- 实现 subtitle-grade streaming（字幕级低延迟流式刷新）。
- 目标是录音中像视频会议字幕一样低延迟逐字或逐短语刷新，并允许句子被持续修正。
- 需要清晰区分 ASR partial token（识别中的临时 token）和最终会议原文。
- 需要处理 partial 回退、final 覆盖、滚动定位、长会议性能和跨 provider 行为差异。

### 6. 系统声音采集

- V1 只录麦克风。
- V2 将系统声音采集作为独立方向：支持 system audio capture（系统声音采集），用于 Zoom、Teams、腾讯会议等线上会议中采集对方声音。
- Windows/macOS 的系统音频采集方案需要单独设计，不能假设与麦克风采集同形。
- 需要明确麦克风与系统声音的混音、回声、延迟对齐、权限失败和设备切换策略。

### 7. 悬浮入口与独立实时展示

- 后续计划支持在悬浮球内直接发起会议记录，不要求用户先进入主界面的“会议”页。
- 发起会议记录后，可单独弹窗或悬浮展示实时会议记录内容。
- 弹窗/悬浮展示需要覆盖录音状态、暂停/继续、停止、实时原文和错误状态。
- 需要明确主界面会议页与悬浮展示之间的状态同步：同一场会议只能有一个 active session（活跃会话），多个入口只控制同一会话。
- 需要处理关闭弹窗的行为：关闭展示不应默认停止会议，停止会议必须是明确动作。

### 8. 长会议生成质量增强

- V1 已要求长会议使用 rolling context（滚动上下文），避免孤立分段总结。
- 后续可进一步做分段笔记可视化、引用回溯、待办去重说明和结论置信度。
- 需要评估超长会议的上下文压缩策略，避免关键决策或负责人在压缩过程中丢失。

### 9. 更多导出与集成

- 在 Markdown 导出基础上，后续可支持 Word/PDF 导出。
- 可评估导出结构化待办到第三方任务系统，但这涉及账号、授权、失败重试和同步状态，不属于 V1。

### 10. 上传音频生成会议记录

- 后续支持用户上传已有音频文件生成会议记录，不要求必须通过 OpenLess 现场录音。
- 上传音频应复用会议记录数据结构：生成 `MeetingRecord`（会议记录）、`TranscriptSegment`（会议原文片段）和后续 summary（总结）。
- 需要明确支持的音频格式、大小限制、时长限制、转码策略、失败重试和本地临时文件清理。
- 需要评估上传音频与现有会议录音音频保留策略的关系：上传原文件是否复制到 `meeting-recordings/`、是否计入 retention（保留数量）、用户删除会议时是否删除上传副本。
- 不应绕开现有 ASR provider（语音转文字服务商）选择逻辑；如需独立配置，应归入会议专用 ASR 配置方向统一设计。

## 当前结论

后续能力应保持独立拆分，不混入 `meeting-recording-v1-spec.md` 的 V1 实施范围。

V1 优先保证：

- 会议模式独立入口。
- 麦克风录音和实时滚动原文。
- 会后 LLM 总结与结构化待办。
- 本地会议记录管理。
- 音频保留与重新转写。
