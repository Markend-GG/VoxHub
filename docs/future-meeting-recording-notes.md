## 背景

会议录音总结 V1 先做独立会议模式：麦克风录音、实时滚动原文、会后 LLM 总结待办、本地会议记录、Markdown 导出、原始音频按最近 N 场保留。

以下能力在需求讨论中被确认有后续价值，但不进入 V1 成功标准。本文只做备忘，避免后续继续讨论时遗忘方向。

## 后续方向

### 1. 会议专用 ASR 配置

- 为会议模式提供独立 ASR provider（语音转文字服务商）配置，不再完全复用全局短口述 ASR。
- 支持在线 ASR 和本地 ASR 在会议模式内同时作为可选项，并允许用户选择、切换。
- 会议模式需要独立保存 ASR 配置，不影响现有短口述链路。
- 需要处理会议中切换 provider 的边界：是否允许热切换、切换时是否产生新分段、旧 provider 失败如何标记。

### 2. VAD 与更自然的分段

- 接入 VAD（Voice Activity Detection，语音活动检测）优化会议原文分段。
- 目标是让段落按自然停顿生成，而不是完全依赖 ASR final segment（语音识别最终片段）。
- 需要评估 VAD 与不同 ASR provider 的职责边界：由 ASR 返回分段，还是 OpenLess 本地先切音频。
- 需要避免 VAD 误切导致语义断裂，尤其是中文短停顿和多人抢话场景。

### 3. 说话人分离

- 接入 speaker diarization（说话人分离），把 V1 默认的“未区分”升级为“发言人 1 / 发言人 2 / ...”。
- 支持实时区分发言人：会议进行中界面直接显示“发言人 A / B / C”等标签。
- 会议结束后继续保留说话人标签，会议原文、总结引用和导出内容都能带上说话人信息。
- 需要支持会后手动重命名说话人，例如把“发言人 1”改成真实姓名。
- 需要明确说话人标签的可信度：低置信度片段应允许显示为“未确认”或保留原标签。
- V2-2 已确认设置提供独立的会后 ASR 模型下拉，以及关闭、云端处理、本地处理三态说话人选项；预计发言人数在开始会议时选择并快照到单场会议。
- V2-2 会后 ASR 默认 `fun-asr`、备选 `paraformer-v2`，不扩展其他会后模型；失败不自动切换。本地说话人处理使用独立模型，只与所选会后 ASR 生成的整理后原文时间戳对齐。
- V2-2 首版只做会后处理；实时 speaker label（实时说话人标签）继续留在 V3。
- 云端 / 本地成本、延迟、隐私与准确率比较已进入 `docs/meeting-recording-v2-2-diarization-plan.md` 的真实验收矩阵，不能只做概念评估。

### 4. 实时标点与文本清理

- V1 实时区域展示 ASR 原始结果，结束后统一清理标点和分段。
- 后续可接入实时 punctuation restoration（标点恢复）和 text normalization（文本规范化）。
- 需要避免实时文本频繁回写造成闪动、滚动位置跳动和用户误以为内容已最终确认。
- 可考虑 UI 上区分 partial（临时片段）和 final（最终片段）。

### 5. 字幕级低延迟流式体验

- 实现 subtitle-grade streaming（字幕级低延迟流式刷新）。
- 目标是录音中像视频会议字幕一样低延迟逐字或逐短语刷新，并允许句子被持续修正。
- 需要清晰区分 ASR partial token（识别中的临时 token）和最终会议原文。
- 需要处理 partial 回退、final 覆盖、滚动定位、长会议性能和跨 provider 行为差异。

### 6. 系统声音采集

- V1 只录麦克风。
- 2026-08-14 用户已明确要求继续开发该能力，已从未拆解 future 方向进入独立 V3-2 计划：`docs/meeting-recording-v3-2-system-audio-capture-plan.md`。
- V3-2 支持 system audio capture（系统声音采集），用于腾讯会议、飞书会议、微信语音等线上会议中采集对方声音。
- Windows/macOS 的系统音频采集方案需要单独设计，不能假设与麦克风采集同形。
- 需要明确麦克风与系统声音的混音、回声、延迟对齐、权限失败和设备切换策略。
- 当前状态仍为 `missing`（未实现）；验收状态见 `docs/meeting-recording-v3-2-system-audio-capture-acceptance-checklist.md`。

### 7. 悬浮入口与独立实时展示

2026-07-18 更新：其中“会议期间的可见状态与暂停 / 继续 / 停止控制”已拆为独立的会议桌宠 V1，范围以 `docs/meeting-companion-v1-spec.md` 为准。桌宠 V1 不包含从悬浮窗新建会议和实时原文展示，以下未被新 spec 覆盖的能力仍属于 future。

- 后续计划支持在悬浮球内直接发起会议记录，不要求用户先进入主界面的“会议”页。
- 发起会议记录后，可单独弹窗或悬浮展示实时会议记录内容。
- 弹窗/悬浮展示需要覆盖录音状态、暂停/继续、停止、实时原文和错误状态。
- 需要明确主界面会议页与悬浮展示之间的状态同步：同一场会议只能有一个 active session（活跃会话），多个入口只控制同一会话。
- 需要处理关闭弹窗的行为：关闭展示不应默认停止会议，停止会议必须是明确动作。

### 8. 长会议生成质量增强

- V1 已要求长会议使用 rolling context（滚动上下文），避免孤立分段总结。
- 后续可进一步做分段笔记可视化、引用回溯、待办去重说明和结论置信度。
- 需要评估超长会议的上下文压缩策略，避免关键决策或负责人在压缩过程中丢失。

### 9. 更多导出与集成

- 在 Markdown 导出基础上，后续可支持 Word/PDF 导出。
- 可评估导出结构化待办到第三方任务系统，但这涉及账号、授权、失败重试和同步状态，不属于 V1。

### 10. 上传音频生成会议记录

- 已确认后续版本需要支持用户上传已有音频文件生成会议记录，不要求必须通过 OpenLess 现场录音。
- 该能力可作为会议 V2 候选方向之一，建议与现场录音、system audio capture（系统声音采集）解耦设计。
- 上传音频应复用会议记录数据结构：生成 `MeetingRecord`（会议记录）、`TranscriptSegment`（会议原文片段）和后续 summary（总结）。
- V2-3 已确定用户源文件只读；应用先流式复制 / 解码到受管 `meeting-recordings/<meeting-id>/part-0001.wav`，后续任务不依赖源文件继续存在。
- 导入音频按所选 ASR 模型类型动态路由：`fun-asr` / `paraformer-v2` 等云端模型走文件流上传，本地模型走本地 batch ASR engine（批量识别引擎）；说话人处理方式作为独立配置叠加。
- 首批必须支持标准 PCM WAV；其他压缩格式需要 decoder（解码器）跨平台 POC 通过后才能开放，不能依赖用户自行安装 `ffmpeg`。
- 导入副本与现场录音使用同一 retention（保留数量），但 processing hold（处理占用）期间不能被清理；删除会议只删除受管副本，不删除用户源文件。
- 详细流程、取消、重试、应用重启恢复和失败清理见 `docs/meeting-recording-v2-3-audio-import-plan.md`。

### 11. 会议纪要融入日报

- 日报生成可以把指定时间范围内的会议纪要作为一种独立材料来源，与语音历史、重写历史和截图记录共同参与生成。
- 优先使用 `MeetingRecord`（会议记录）中的标题、开始 / 结束时间、总结概述、关键决策、待办和风险；会议原文是否参与生成作为后续产品选项，不默认把整段长原文全部送入模型。
- 日报必须保留来源差异：会议中“讨论过的内容”不能直接写成用户“已经完成的成果”；只有纪要中有明确完成、确认、提交或交付证据时，才能写入进展 / 成果。
- 需要在报告来源统计中增加会议数量，并支持从日报内容回溯到具体会议记录，便于核对结论和待办。
- 手动生成日报和定时日报应复用同一套会议材料收集逻辑，避免同一天生成结果口径不同。
- 会议纪要生成失败时的降级策略待确认：可选择跳过、只使用标题和原文摘要，或提示用户先重试会议总结。
- 待确认的产品选项：默认自动纳入当天全部会议，还是由用户在生成日报时选择会议；当前只确认“可以融入日报”，不预设默认行为。

### 12. MCP / CLI 只读获取会议记录

- 为支持 MCP（Model Context Protocol，模型上下文协议）的 AI 软件和命令行自动化，提供统一的本地会议记录查询能力；MCP 与 CLI（Command-Line Interface，命令行接口）复用同一查询服务，不各自读取持久化文件。
- 建议的最小查询范围：按时间范围列出会议、按会议 ID 获取详情、按标题 / 纪要 / 原文关键词搜索。
- 默认可返回标题、时间、时长、状态、结构化纪要、待办、风险和原文片段；长原文应支持分页或显式 `includeTranscript`（包含原文）参数，避免一次返回过多内容。
- MCP 工具名和 CLI 命令名仅作为后续 spec 候选，例如 `list_meetings`、`get_meeting`、`search_meetings`，以及 `openless meetings list|get|search`，实现前再确认稳定命名和参数。
- CLI 至少支持 JSON 机器可读输出；可选 Markdown 人类可读输出。错误信息写入标准错误流，并使用非零退出码表示失败。
- 第一阶段严格只读，不提供删除会议、修改纪要、开始 / 停止录音等写操作，避免外部 AI 软件误操作会议数据。
- 默认不返回音频二进制、音频文件绝对路径、模型凭据、日志或其他本地隐私数据；如未来开放音频读取，必须单独授权和设计访问边界。
- 接口默认仅在本机可用，并需要明确分页、结果上限、字段裁剪、并发读取和会议正在写入时的一致性行为。
- 验收时需覆盖：无会议、单场会议、多场分页、长原文、总结失败、记录删除后查询、中文路径，以及 MCP / CLI 输出字段一致性。

### 13. 统一会议查询层

- 日报、MCP 和 CLI 都依赖同一套会议查询与字段裁剪能力，建议先建立只读应用服务，再分别接入报告生成器、MCP transport（传输层）和 CLI 参数解析。
- 查询层继续通过现有会议持久化模块读取 `MeetingRecord`，不允许外部集成直接解析或修改内部 JSON 文件，避免持久化格式升级后接口失效。
- 对外输出使用独立、可版本化的数据结构，明确字段含义、时间格式、缺省值和兼容策略；内部 `MeetingRecord` 增加字段时，不应无意扩大外部可见数据范围。

## 当前阶段归属（2026-08-12）

- V2-1：会议专用 ASR 配置、`fun-asr-realtime` realtime ASR（实时语音转文字）、draft + final（临时识别 + 最终片段）、timestamp metadata（时间戳元数据）。
- V2-2：停止会议后默认用 `fun-asr`、可改选 `paraformer-v2` 重新识别完整音频；说话人处理可关闭、使用云端结果或执行本地 diarization 与 transcript alignment（原文对齐）。
- V2-3：用户从本机导入音频生成会议记录；后端按 ASR 模型 descriptor（描述符）动态路由云端接口或本地引擎，并按兼容矩阵叠加关闭 / 云端 / 本地说话人处理；复用 V2-2 状态机、revision（修订版本）和音频生命周期。
- 已进入独立 V1 spec：会议桌宠的可见录音状态、暂停 / 继续 / 停止控制、拖动和安全隐藏。
- V3 / future：realtime speaker labels（实时说话人标签）、subtitle-grade streaming（字幕级低延迟流式刷新）、从悬浮入口新建会议、独立实时原文展示、长会议总结质量增强、Word/PDF 导出、第三方任务系统集成、高级文本后处理、会议纪要融入日报，以及 MCP / CLI 只读获取会议记录。system audio capture（系统声音采集）已进入独立 V3-2 计划，不再是未拆解备忘项。

## 当前结论

后续能力应保持独立拆分，不混入 `meeting-recording-v1-spec.md` 的 V1 实施范围。

V1 优先保证：

- 会议模式独立入口。
- 麦克风录音和实时滚动原文。
- 会后 LLM 总结与结构化待办。
- 本地会议记录管理。
- 音频保留与重新转写。
